# ทดสอบ RouteAlert แบบหลายผู้ใช้พร้อมกัน

เครื่องมือจำลองผู้แจ้งเหตุ โรงพยาบาล และรถพยาบาลจำนวนมากที่ใช้งานระบบ **พร้อมกัน** แล้วตรวจว่าข้อมูลไม่ตีกัน
พร้อมวัดเวลา ผลลัพธ์ออกมาเป็นรายงานภาษาไทย (`results/report-*.md`) ใช้ประกอบเล่มวิทยานิพนธ์ได้ทันที

ผู้ใช้จำลองแต่ละคนใช้ Firebase app แยกกัน (การเชื่อมต่อ, listener, cache ของตัวเอง) เหมือนมือถือคนละเครื่อง
และทำตามตรรกะเดียวกับโค้ดแอปทุกขั้น เช่น เลือกโรงพยาบาลด้วยสูตรระยะทางเดียวกับ `latlong2` ของแอป, transaction
รับเคสแบบเดียวกับ `dispatchIncidentByHospital`, การเลื่อนสถานะ, ETA และ "รถใกล้ถึง" ตาม `ambulance_home_screen.dart`

## ทดสอบทุกสถานการณ์ในคำสั่งเดียว (S01–S19 + G01–G20)

รายการ 39 สถานการณ์ที่มีโอกาสเกิดจริง (S = หลายผู้ใช้ 19 ข้อ, G = GPS และตำแหน่ง 20 ข้อ) (ใคร ทำอะไร ผลที่ต้องได้ ทดสอบด้วยอะไร) อยู่ใน [`docs/TEST_SCENARIOS.md`](../../docs/TEST_SCENARIOS.md)
ทุกข้อทดสอบอัตโนมัติ — ข้อทดสอบใน Dart, Worker และตัวจำลองติดรหัส `[Sxx]` แล้วรวมผลเป็นรายงานเดียวรายสถานการณ์

```bash
cd route-alert-app
tools/run_all_scenarios.sh           # Dart + Worker + ตัวจำลอง → tools/multi_user_sim/results/scenarios-*.md
tools/run_all_scenarios.sh --quick   # เฉพาะ Dart + Worker (~1 นาที)
tools/run_all_scenarios.sh --legacy  # ตัวจำลองใช้ตรรกะก่อนแก้ — แสดงว่าชุดทดสอบจับบั๊กเดิมได้
tools/run_all_scenarios.sh --results # ผลการทดลองสำหรับเล่ม: ตัวจำลอง 3 รอบ + ก่อนแก้ 1 รอบ → docs/TEST_RESULTS.md
```

เพิ่ม/แก้สถานการณ์: แก้ `src/catalog.mjs` แล้วติดรหัสเดียวกันในชื่อเทสต์ (`test('[S21] ...')`) หรือ `sid` ของ check ในตัวจำลอง
จากนั้นสร้างเอกสารใหม่ด้วย `node src/scenario_report.mjs --doc=../../docs/TEST_SCENARIOS.md`

## สิ่งที่ทดสอบ (ตัวจำลอง)

| คำสั่ง | สถานการณ์ | ตรวจอะไร |
|---|---|---|
| `burst` | ผู้แจ้ง 20 คนกดแจ้งเหตุในเวลาเดียวกัน | ไม่มีเคสหาย, รูปแบบเอกสารถูก, ทุกเคสส่งถึงโรงพยาบาลที่ใกล้ที่สุดตามกฎของแอป, ทุกเครื่องโรงพยาบาลเห็นครบ, เวลาที่ใช้ |
| `race` | รถ 5 คันกด "รับเคส" เคสเดียวกันพร้อมกัน 10 รอบ (ครึ่งหนึ่งมีโรงพยาบาลสั่งจ่ายคันแรกแข่งด้วย) | เคสเดียวรับได้หลายคัน: ทุกคันที่แอปบอกว่าสำเร็จอยู่ในเคสจริง (ไม่มีการเขียนทับ), นับจำนวนรถตามทะเบียนถูก, รพ. ได้คันแรกเฉพาะตอนเคสยังว่าง, กดซ้ำไม่เขียนซ้ำ, เคสที่ปิดแล้วสั่งจ่ายไม่ได้, ยืนยันว่าแย่งกันจริงใน transaction |
| `isolation` | โรงพยาบาล 3 แห่ง แจ้งเหตุกระจายทุกพื้นที่ | แต่ละโรงพยาบาลเห็นเฉพาะเคสของตัวเองและเห็นครบ, บัญชีเก่าที่ไม่มีโรงพยาบาลเห็นทั้งหมด |
| `lifecycle` | 10 เคสวิ่งครบวงจรพร้อมกัน: แจ้ง → โรงพยาบาลส่งรถใกล้สุด (กองรถผ่าน MQTT) → รถวิ่ง ส่ง ETA → ใกล้ถึง → ถึงจุดเกิดเหตุ → นำส่ง → ใกล้ถึง รพ. → จบ | ทุกเคสจบ, ไม่เปลี่ยนรถกลางทาง, สถานะไม่ถอยหลัง, เคสที่จบไม่ถูกเปิดกลับ, "ใกล้ถึง" ครั้งเดียว, **เครื่องของผู้แจ้งแต่ละคน**เห็นเคสตัวเองครบทุกสัญญาณ (มีรถรับ/ETA/ใกล้ถึง/จบ), วัดว่ารถถือเคสซ้อนกี่เคส |
| `risks` | จุดเสี่ยงสองข้อที่พบ (ดูหัวข้อ "สิ่งที่พบ") โดยให้ฝ่ายที่สองลงมือหลังฝ่ายแรก 0, 25, 50 … 1600 ms | ตรรกะปัจจุบัน: ต้องไม่เกิดเลยทุกช่วงเวลา · `--app-logic=legacy`: วัดว่าห่างกันได้มากสุดกี่ ms ที่ยังเกิด |
| `edge` | สถานการณ์เฉพาะ S03, S05, S07, S08, S11–S14, S16, S18 (แจ้งซ้ำ, ER เต็ม, เครื่องเปิดทีหลัง, หลายเครื่อง/หลายบัญชี, รถออฟไลน์ผ่าน MQTT, ร่วมรับเคส, ยกเลิกชนการรับเคส) | ดู `docs/TEST_SCENARIOS.md` |
| `all` | รันทุกข้อข้างบนต่อกัน แล้วล้างข้อมูลจำลอง | |

ในรายงาน ✅ = ผ่าน, ❌ = ไม่ผ่าน, 📊 = วัดค่า (ไม่มีผ่าน/ไม่ผ่าน), ☑️ = ตรวจว่าตัวจำลองสร้างข้อมูลถูกรูปแบบแอป
(ไม่ได้ทดสอบพฤติกรรมของระบบ จึง**ไม่นับ**ในจำนวนข้อที่ผ่าน)

พฤติกรรมคนที่จำลองไว้ (เพื่อไม่ให้ผลดีหรือแย่เกินจริง):
- ผู้แจ้งหนึ่งคนแจ้งหนึ่งเคสต่อเครื่อง (แอปมี cooldown 2 นาทีต่อเครื่อง)
- เจ้าหน้าที่โรงพยาบาลกดสั่งจ่ายหลังเห็นเคส 0.75–2.25 วินาที (สุ่ม, `--dispatch-delay-ms=1500` คือค่ากลาง) ไม่ใช่ทันทีที่ข้อมูลมาถึง
- ถ้าสั่งจ่ายไม่สำเร็จ (รถถูกแย่ง) แอปแค่แสดงข้อความ — ตัวจำลองถือว่าเจ้าหน้าที่กดส่งใหม่หลังรอเท่าเดิม
- ETA: ค่าเริ่มต้นจำลองว่าได้เส้นทางจาก OSRM (ส่ง ETA ตามรอบปกติ) · `--route-mode=fallback` จำลอง OSRM ล่ม ซึ่งแอปถือว่าเป็นค่าประมาณและส่งครั้งเดียวต่อช่วงทาง
- จบแต่ละสถานการณ์จะปิด "มือถือ" ทุกเครื่องของสถานการณ์นั้น ไม่ให้ listener ค้างไปอ่านข้อมูลของสถานการณ์ถัดไป
| `cleanup` | ลบข้อมูลจำลองที่ค้าง | ลบเฉพาะเอกสารที่ id ขึ้นต้น `SIM-` **และ** มี `simulation: true` |

นอกจากนี้ที่ `route-alert-app/test/multi_user_concurrency_test.dart` มีเทสต์ 12 ข้อที่รัน **โค้ด Dart จริงของแอป**
(`IncidentService`) ด้วยผู้ใช้หลายคนพร้อมกัน (รันด้วย `flutter test`)

## ความปลอดภัยของข้อมูล

- ค่าเริ่มต้นคือ **Firestore Emulator ในเครื่อง** (project `demo-routealert`) ไม่แตะ Firebase จริงเลย
- จะรันกับ Firebase จริงได้ต้องใส่ `--target=prod --i-understand-this-writes-to-production` เองเท่านั้น
- ทุกการเขียน/ลบผ่านตัวกันที่ยอมให้แตะได้เฉพาะเอกสารที่ id ขึ้นต้น `SIM-` (เคส `SIM-Case #AVCB…`, รถ `SIM-AMB-…`, โรงพยาบาล `SIM-HOSP-…`) และเอกสารใหม่ต้องมี `simulation: true`
- ผู้แจ้งจำลองใช้อีเมล `sim-reporter-…@routealert.test`
- MQTT บน emulator ใช้ broker ในเครื่อง; บนระบบจริงใช้ **topic แยกของรอบนั้น** เป็นค่าเริ่มต้น (มือถือจริงไม่เห็นรถจำลอง) — ถ้าจะให้รถจำลองขึ้นบนเรดาร์มือถือจริงต้องใส่ `--real-topic --i-understand-real-phones-will-alert` ซึ่ง **จะทำให้มือถือผู้ขับขี่จริงแจ้งเตือนและโรงพยาบาลจริงเลือกส่งรถจำลองได้**
- หลังรันเสร็จจะล้างข้อมูลของรอบนั้นอัตโนมัติ (ใส่ `--keep` ถ้าต้องการเก็บไว้ดู) และรายงานยืนยันว่าเหลือ 0 — ล้างให้ด้วยแม้สถานการณ์จะล้มกลางทางหรือกด Ctrl-C
  (ยกเว้นโปรแกรมถูกฆ่าทันที เช่น `kill -9` หรือไฟดับ — ให้รัน `cleanup` เองอีกครั้ง)

## วิธีรันบนเครื่อง (emulator)

ต้องมี Node 20+, Firebase CLI และ Java (JDK 11+) สำหรับ emulator

```bash
cd route-alert-app/tools/multi_user_sim
npm install
npm run test:unit        # ตรวจสูตรคำนวณกับค่าจริงจาก Dart
npm run test:emulator    # รันทุกสถานการณ์ (~4 นาที) แล้วดูรายงานใน results/
```

ถ้าไม่มี Java: ติดตั้ง JDK (เช่น Temurin 21) หรือตั้ง `JAVA_HOME` ไปที่ JDK ที่มี แล้วใส่ `$JAVA_HOME/bin` ใน `PATH`
รันทีละสถานการณ์: `npm run emu -- "$(which node) src/cli.mjs race --target=emulator --ambulances=8"`
(ต้องใส่ path ของ node ตรงๆ เพราะ Firebase CLI แบบไฟล์เดียวมี node ของตัวเองที่เก่ากว่า)
ถ้า Firebase CLI ค้างตอนเริ่ม emulator: `./run-emulator.sh all --target=emulator` (รัน jar ของ emulator ตรงๆ)

ผลก่อน/หลังแก้บั๊ก: `--app-logic=legacy` จำลองตรรกะรับเคส/เลื่อนสถานะแบบเดิม (ก่อนแก้) ค่าเริ่มต้นคือตรรกะปัจจุบัน
รันทั้งสองแบบแล้วเทียบรายงาน เช่น `./run-emulator.sh risks --target=emulator --app-logic=legacy`

> ตัวเลขเวลาไวต่อภาระของเครื่อง — ปิดโปรแกรมหนักๆ (เกม, build) ก่อนรัน `lifecycle` เพราะใช้เวลาจำลองเร่ง 20 เท่า
> ถ้าเครื่องทำงานหนัก รถจำลองจะเดินช้าจนเคสจบไม่ทันเวลา (ไม่ใช่บั๊กของแอป) — ลด `--time-scale` หรือเพิ่ม `--lifecycle-timeout-ms`

## รันกับ Firebase จริง (ตอนทดสอบกับอาจารย์)

```bash
node src/cli.mjs all --target=prod --i-understand-this-writes-to-production --with-mqtt
node src/cli.mjs cleanup --target=prod --i-understand-this-writes-to-production   # ถ้ามีอะไรค้าง
```

- ใช้รายชื่อโรงพยาบาลจริงใน `hospital_profiles` (อ่านอย่างเดียว) ต้องมีอย่างน้อย 2 แห่ง — หรือใส่ `--seed-hospitals` ให้สร้างโรงพยาบาลจำลอง (ระหว่างรัน โรงพยาบาลจำลองจะอยู่ในรายชื่อของแอปจริงด้วย)
- ระหว่างรัน มือถือจริงที่เปิดแอปอยู่จะเห็นเคสจำลอง (`SIM-…`) ในรายการ — ตั้งใจให้เห็นได้ถ้าอยากโชว์ ถ้าไม่อยากให้เห็นให้ปิดแอปไว้
- ตัวเลขเวลาจากระบบจริงคือค่าที่ควรใส่ในเล่ม (emulator ไม่มีเครือข่ายจริง จึงเร็วกว่าความจริง)
- ค่าใช้จ่ายโดยประมาณของ `all` ค่าเริ่มต้น (โปรแกรมพิมพ์ให้ดูก่อนรันทุกครั้ง): เขียน ~760 · อ่าน ~12,000 ครั้ง (วัดจริงบน emulator: เขียน ~750 · อ่าน ~9,000) — โควตาฟรีต่อวันของ Firestore คือเขียน 20,000 / อ่าน 50,000 จึงรันได้หลายรอบต่อวัน
  ถ้าจะเพิ่มจำนวนผู้ใช้ ระวัง `lifecycle` ที่การอ่านโตแบบกำลังสอง (ทุกเครื่องฟังทุกการเขียน)

ตัวเลือกปรับขนาด: `--reporters=20 --ambulances=5 --rounds=10 --hospitals=3 --cases-per-hospital=4 --cases=10 --risk-trials=3 --risk-delays=0,25,50,100,200,400,800,1600 --dispatch-delay-ms=1500 --route-mode=osrm`

## สิ่งที่พบจากการทดสอบ และการแก้ไข

การทดสอบหลายผู้ใช้เจอจุดเสี่ยงสองข้อในโค้ดแอป **แก้แล้วทั้งคู่** (ผลก่อน/หลังแก้ดูได้จาก `--app-logic=legacy`):

1. **รถคันเดียวถูกสั่งให้ไปสองเคสพร้อมกันได้** — โรงพยาบาลสองแห่งสั่งจ่ายรถว่างคันเดียวกันให้คนละเคส
   ก่อนที่เครื่องที่สองจะรู้ว่ารถคันนั้นถูกใช้แล้ว เพราะ transaction เดิมล็อกแค่เอกสารเคส (เว็บ Agency ไม่เช็ครถว่างเลย)
   - แก้: เพิ่มเอกสาร `ambulance_locks/{ทะเบียนรถ}` ที่ transaction รับเคสอ่าน/เขียนคู่กับเอกสารเคส — ถ้าล็อกชี้ไปเคสอื่นที่ยังไม่จบ
     และมีรถคันนี้อยู่ = ปฏิเสธ ("รถไม่ว่าง") ล็อกที่ชี้ไปเคสที่จบ/ถูกปิดแล้วถือว่าว่าง จึงไม่ต้องมีใครคอยปลดล็อก
   - เว็บ Agency กรองรถที่มีเคสค้างออกก่อนเลือกคันใกล้สุดแล้ว
2. **เคสที่โรงพยาบาลปิดแล้วถูกเปิดกลับได้** — รถกดเลื่อนสถานะก่อนเครื่องรถจะรู้ว่าเคสถูกปิด เพราะการเลื่อนสถานะเดิมเขียนทับตรงๆ
   - แก้: เลื่อนสถานะเป็น transaction ที่เดินหน้าอย่างเดียว ไม่แตะเคสที่ปิด/จบแล้ว และคำนวณขั้นจากสถานะเสมอ
     (เดิม "เคสจบ" เป็นขั้น 5 จากหน้าหลัก แต่ขั้น 4 จากหน้ารายละเอียด)

ตัวเลขใน `risks` แบบ legacy คือ **ช่วงเวลาเสี่ยง** (ฝ่ายที่สองลงมือหลังฝ่ายแรกไม่เกินกี่ ms แล้วยังเกิดปัญหา = เวลาที่อีกเครื่องใช้รับข้อมูลใหม่)
บน emulator ในเครื่องได้ ~0–50 ms และกว้างขึ้นเมื่อเครื่องทำงานหนัก บนเครือข่ายมือถือจริงคาดว่ากว้างกว่านี้มาก
หลังแก้ต้อง **ไม่เกิดเลยทุกช่วงเวลา** เพราะไม่ขึ้นกับว่าอีกเครื่องเห็นข้อมูลช้าแค่ไหน

**เคสเดียวรับได้หลายคัน** (เพิ่มพร้อมการแก้ข้างบน): รถคันอื่นกด "ร่วมรับเคส" ได้จนกว่าจะเริ่มนำส่ง, โรงพยาบาลกด "ส่งรถเพิ่ม" ได้
นับจำนวนรถตาม**ทะเบียน** (หลายบัญชีบนรถคันเดียวกัน = 1 คัน) ทุกฝั่งเห็น "กำลังดำเนินเคส N คัน"
ถ้ารถหลายคันกดพร้อมกันมากๆ transaction จะชนกันและบางคันได้ข้อความ "ไม่สำเร็จ ลองใหม่" (optimistic concurrency ของ Firestore ลองได้ 5 รอบ)
— ไม่มีคันไหนถูกเขียนทับหาย ตรวจใน `race`

⚠️ ต้อง deploy `firestore.rules` ใหม่ (มี `ambulance_locks`) — ถ้ายังไม่ deploy แอปจะทำงานต่อแบบไม่มีล็อกรถ (บั๊กข้อ 1 ยังเกิดได้)

สิ่งที่ควรรู้อื่นๆ: broker MQTT ถูกกำหนดตายตัวในโค้ด (`broker.emqx.io`) ไม่ได้อ่านจาก `.env` และไม่มีการยืนยันตัวตน

## ทดสอบด้วยมือถือจริงหลายเครื่อง (ต่อหน้าอาจารย์)

เตรียมบัญชี: โรงพยาบาล A และ B (คนละโรงพยาบาล ปักหมุดห่างกัน), รถพยาบาล R1 และ R2 (คนละทะเบียน; R1 ล็อกอินได้สองเครื่อง),
R1b = อีกบัญชีที่ตั้งทะเบียน**เดียวกับ R1** (เจ้าหน้าที่อีกคนบนรถคันเดียวกัน), ผู้แจ้ง D1 และ D2
ติดตั้งแอปแบบ Release ทุกเครื่องภายใน 7 วันก่อนทดสอบ (บัญชี Apple ฟรี) และเปิด "แจ้งเตือนพื้นหลัง" ในเครื่องผู้แจ้ง

| # | ใครทำอะไร | ผลที่ต้องเห็น |
|---|---|---|
| 1 | D1 แจ้งเหตุใกล้โรงพยาบาล A, D2 แจ้งเหตุใกล้โรงพยาบาล B ในเวลาใกล้กัน | A เห็นเฉพาะเคสของ D1, B เห็นเฉพาะเคสของ D2 (แจ้งเตือนขึ้นเฉพาะโรงพยาบาลนั้น) · รถทุกคันเห็นทั้งสองเคส |
| 2 | R1 กด "ยืนยันรับเคส" เคสของ D1 | D1 ได้ "รถพยาบาลกำลังเดินทางไปหาคุณ" · ทุกฝั่งเห็น "กำลังดำเนินเคส 1 คัน" |
| 3 | R2 กด "ร่วมรับเคส (+1 คัน)" เคสเดียวกัน → ยืนยัน | ทุกฝั่งเห็น "2 คัน: (ทะเบียน R1), (ทะเบียน R2)" · D1 ได้ "มีรถพยาบาลมาเพิ่ม" |
| 4 | R1b กดร่วมรับเคสเดียวกัน | ยังเป็น **2 คัน** (นับตามทะเบียน ไม่ใช่ตามบัญชี) · R1b เลื่อนสถานะเคสนี้ได้ |
| 5 | B กด "ส่งรถพยาบาล" ให้เคสของ D2 และ A กด "ส่งรถเพิ่ม" ที่เคสของ D1 | ไม่ส่ง R1/R2 ซ้อน (ขึ้นว่ารถกำลังปฏิบัติภารกิจอื่น) — ถ้ามีรถคันที่สามว่าง ระบบเลือกคันนั้น |
| 6 | ล็อกอินบัญชี R1 อีกเครื่อง | เห็นเคสของ D1 เป็นของตัวเองและเลื่อนสถานะได้ (ไม่ขึ้น "เคสของหน่วยอื่น") |
| 7 | R1 และ R2 วิ่งเข้าหาจุดเกิดเหตุ (หรือใช้ Xcode → Debug → Simulate Location) | D1 เห็น ETA ของ**คันที่ใกล้ที่สุด** (ชื่อรถ + "(+1 คัน)") บนหน้าติดตาม/หน้าล็อก/Dynamic Island, คันแรกที่เหลือ < 500 ม. ทำให้ได้ "รถพยาบาลใกล้ถึงแล้ว" ครั้งเดียว |
| 8 | R2 กดถึงจุดเกิดเหตุ → นำส่ง แล้ว R1 กด "ถึงจุดเกิดเหตุ" ทีหลัง | สถานะไม่ถอยกลับ (ยังเป็นกำลังนำส่ง) · ถึงโรงพยาบาลแล้ว D1 ได้ "✅ เคสของคุณเสร็จสิ้นแล้ว" และรถทุกคันว่างรับเคสใหม่ได้ |
| 9 | A กด X ที่เคสที่มีรถแล้ว → "ปิดเคส (ทุกฝั่ง)" แล้วรถกดเลื่อนสถานะ | กล่องยืนยันบอกจำนวนรถ, เคสหายจากทุกเครื่อง, รถที่กดเลื่อนสถานะได้ "เคสนี้ถูกปิดหรือจบไปแล้ว" (เคสไม่กลับมาเปิด) |
| 10 | D1 ออกจากหน้าติดตามแล้วเข้าใหม่จากแท็บ "รายงานของฉัน" | เห็นประวัติทุกเคส รวมเคสที่จบ/ยกเลิก และหน้าติดตามอัปเดตสด |
